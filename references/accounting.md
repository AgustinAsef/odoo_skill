# Accounting — Odoo 18.0

Source of truth: `Versiones/V18/odoo-18.0/addons/account/models/account_move.py`,
`account_tax.py`, `account_account.py`, `account_report.py`, `chart_template.py`;
`Versiones/V18/odoo-18.0/addons/l10n_ar/` (a real localization); root `CLAUDE.md`
(`accountant` dependency rule). `account.report`/`account.report.line`/
`account.report.expression` are core `account` (not Enterprise) —
`Versiones/V18/enterprise-18.0/account_reports/` only *extends* them
(`_inherit`) with the reporting engine/UI and localized report XML.

## Core model map

| Model | Role | Key fields |
|---|---|---|
| `account.move` | the document — invoice, bill, credit note, or a plain journal entry | `move_type`, `state` (draft/posted/cancel), `journal_id`, `partner_id`, `invoice_line_ids` (filtered `line_ids`), `line_ids`, `amount_total`, `currency_id` |
| `account.move.line` | one journal item / invoice line | `account_id`, `debit`, `credit`, `balance`, `partner_id`, `tax_ids` (taxes applied to this line), `tax_tag_ids`, `tax_line_id` (set on lines *generated by* a tax), `reconciled` |
| `account.journal` | where entries post — sequence, default accounts | `type` (sale/purchase/cash/bank/general), `code`, `default_account_id` |
| `account.account` | one GL account | `code`, `name`, `account_type`, `reconcile`, `currency_id`, `group_id` (computed from code) |
| `account.tax` | a tax definition | `amount_type`, `type_tax_use`, `price_include_override`, `invoice_repartition_line_ids`, `refund_repartition_line_ids` |
| `account.tax.repartition.line` | where each slice of a tax posts | `repartition_type`, `factor_percent`, `account_id`, `tag_ids` |
| `account.fiscal.position` | remaps taxes/accounts per partner (country, VAT, zip) | `auto_apply`, `country_id`, `vat_required`, `tax_ids`, `account_ids` |
| `account.account.tag` | classification tag on accounts, taxes, or products | `applicability`, `tax_negate`, `country_id` |
| `account.group` | code-range hierarchy grouping accounts for reports | `code_prefix_start`, `code_prefix_end`, `parent_id` |

```python
def is_invoice(self, include_receipts=False):
    return self.is_sale_document(include_receipts) or self.is_purchase_document(include_receipts)

def get_sale_types(self, include_receipts=False):
    return ['out_invoice', 'out_refund'] + (include_receipts and ['out_receipt'] or [])
```
(`account_move.py:5850-5868`)

**Gotcha** (verified, matches workspace memory `odoo-is-invoice-incluye-notas-credito`):
`is_invoice()` — even with `include_receipts=False` — returns `True` for
`out_refund`/`in_refund`. A check meant to mean "this is a *sale* invoice, not a
credit note" must compare `move_type == 'out_invoice'` explicitly; `is_invoice()`
alone does not exclude credit notes.

`is_entry()` is `move_type == 'entry'` — a plain journal entry with no invoice
semantics at all (no due date, no payment terms, doesn't appear in Follow-up/AR
reports the same way).

## Creating and posting invoices from code

Never write `debit`/`credit`/`balance` directly and never build `line_ids` as raw
tuples — see `orm-models.md` `Command`.

```python
invoice = self.env['account.move'].create({
    'move_type': 'out_invoice',
    'partner_id': partner.id,
    'invoice_date': fields.Date.context_today(self),
    'invoice_line_ids': [
        Command.create({
            'product_id': product.id,
            'quantity': 1,
            'price_unit': 100.0,
            # tax_ids left unset -> computed from the product's default taxes
            # (or set explicitly: 'tax_ids': [Command.set(tax.ids)])
        }),
    ],
})
invoice.action_post()
```

- `account.account` and `account.tax` on each line are normally left to compute
  from the product/fiscal position — setting them explicitly bypasses fiscal
  position remapping.
- `action_post()` (`account_move.py:5541-5562`) is the **user-facing** entry
  point: it runs the abnormal-amount/date warning wizard gate, then calls
  `_post(soft=False)`.
- `_post(soft=True)` (`account_move.py:5084`) is the **internal** engine —
  assigns the sequence number, runs the completeness/lock checks, and is what
  `action_post` (and cron auto-post) both call underneath. Call `_post()`
  directly from server code only when you deliberately want to skip the
  wizard gate that `action_post` adds; `_post` itself also gates on
  `account.group_account_invoice` (`account_move.py:5098-5099`).
- `_post` requires `move.is_invoice(include_receipts=True)` handling for the
  quick-edit-total check (`account_move.py:5106`) — so receipts go through the
  same completeness path as invoices even though `is_invoice()` alone (without
  `include_receipts`) would exclude them.

## Declaring a chart template (18.0 `@template` API)

Source: `chart_template.py`. Real example: `addons/l10n_ar/models/template_ar_ri.py`.

```python
from odoo import models, _
from odoo.addons.account.models.chart_template import template

class AccountChartTemplate(models.AbstractModel):
    _inherit = 'account.chart.template'

    @template('ar_ri')
    def _get_ar_ri_template_data(self):
        return {
            'name': _('Argentine Generic Chart of Accounts for Registered Accountants'),
            'parent': 'ar_ex',      # chains onto an existing template
            'code_digits': '12',
            'sequence': 0,
        }

    @template('ar_ri', 'res.company')
    def _get_ar_ri_res_company(self):
        return {
            self.env.company.id: {
                'account_fiscal_country_id': 'base.ar',
                'bank_account_code_prefix': '1.1.1.02.',
                'account_sale_tax_id': 'ri_tax_vat_21_ventas',
            },
        }
```
(`template_ar_ri.py:1-33`)

`@template(template_code, model='template_data')` (`chart_template.py:45-62`) just
registers the decorated function into a per-model, per-template-code list
(`_template_register`, built from `getmembers` over every method carrying
`_l10n_template` — `chart_template.py:69-83`). The function's own body is what
matters; the decorator is bookkeeping, not a data source itself.

**CSV data** lives under `data/template/`, one file per model, suffixed with the
template code: `account.account-ar_ri.csv`, `account.tax-ar_base.csv`,
`account.fiscal.position-ar_ri.csv` (real files under `addons/l10n_ar/data/template/`).
`_parse_csv` (`chart_template.py:1263-1299`) reads `{module}/data/template/{model}
{-{template} if template else ''}.csv`.

**Merging up the parent chain.** `'parent'` in `_get_<code>_template_data` (e.g.
`ar_ri`'s `'parent': 'ar_ex'`) is what makes one template extend another.
`_get_parent_template(code)` (`chart_template.py:1197-1203`) walks `parent` links
into an ordered list `[code, parent, grandparent, ...]`. Both the Python
`@template` registry and `_parse_csv` iterate that list — Python via
`_get_chart_template_data` (`chart_template.py:768`, walks `[None] + parents`,
**`.update(record)` per xmlid** so a child's function can override individual
fields of a parent-declared record without repeating the whole record), CSV via
`_parse_csv` (`chart_template.py:1286`, iterates parents **reversed** so the
most-specific CSV row overwrites the base one for the same `id`).

**Loading**: `try_loading(template_code, company, install_demo=False,
force_create=True)` (`chart_template.py:132-163`) is the public entry point —
resolves the template if not given (guesses from `company.country_id`), then
calls `_load`. `_load` (`chart_template.py:165-248`):

- Requires `self.env.is_system()` — admin only.
- Installs the template's module if not yet installed
  (`module.button_immediate_install()`), then **resets the env/registry**
  (`self.env.reset()`) before continuing — anything held in Python variables
  from before this point is stale.
- `reload_template = template_code == company.chart_template` — calling
  `try_loading` again with the *same* code on a company that already has it is
  a **reload**, not a fresh install: `_pre_reload_data` runs instead of a plain
  create, and existing records get updated rather than duplicated.
- `force_create` controls that reload: `True` creates records that are new
  since the last load; `False` only updates existing ones and skips creating
  new rows (`chart_template.py:143-145` docstring).
- Recurses onto `company.child_ids` at the end (`chart_template.py:247-248`) —
  a template load cascades to sub-companies automatically.

**Data is not retroactive.** A module that adds a *new* `@template`-decorated
function or a new CSV row to a template code that other companies already
loaded does **not** reach those companies on its own — normal module install
only runs data files marked for it, not `_load` again. The only way to backfill
is an explicit `try_loading(code, company, force_create=True)` (or a
`post_init_hook` that does so) after the new module is installed; skipping this
leaves the new accounts/taxes/fields empty on every company that onboarded
before the change existed (workspace memory:
`odoo-chart-template-data-no-retroactiva`).

**Extending an existing template from a new module**: add another
`@template('ar_ri', 'account.tax')`-decorated method (same template code, same
target model) in the new module — its returned dict merges over whatever the
base localization already declared for that xmlid, by the merge rule above.
Don't duplicate the whole base CSV; only declare the delta.

## Taxes and repartition

`account.tax` (`account_tax.py:87` on): `amount_type` (`percent` default —
`fixed`, `percent`, `division` i.e. tax-included percentage, `group` i.e.
combines `children_tax_ids`), `type_tax_use` (`sale`/`purchase`/`none`),
`price_include` is now a **computed** field (`_compute_price_include`,
`account_tax.py:261-269`) derived from `price_include_override`
(`tax_included`/`tax_excluded`/unset) and the company-level default
`company_price_include` — don't set `price_include` directly in 18.0, set
`price_include_override`.

`account.tax.repartition.line` (`account_tax.py:4488` on):

```python
factor_percent = fields.Float(...)                      # % of the base/tax this line carries
repartition_type = fields.Selection([('base', 'Base'), ('tax', 'of tax')], default='tax')
document_type = fields.Selection([('invoice', 'Invoice'), ('refund', 'Refund')], required=True)
account_id = fields.Many2one('account.account', ...)     # where this slice posts
tag_ids = fields.Many2many('account.account.tag', domain=[('applicability', '=', 'taxes')])  # tax grids
```

A tax normally has separate `invoice_repartition_line_ids` and
`refund_repartition_line_ids` (both computed/stored, `account_tax.py:170-181`) —
this is what lets a credit note post the tax to a different account or grid than
the original invoice, and it's why `document_type` exists on the line at all.
`tag_ids` here is how a tax amount reaches a tax report / VAT-book line (see
Reports below) — the `tax_tags` engine on `account.report.expression` reads
these tags off posted `account.move.line.tax_tag_ids`, not off the tax
definition directly.

## `account.fiscal.position`

`partner.py` (`class AccountFiscalPosition`, `:30` on):
`auto_apply` + `country_id`/`country_group_id`/`zip_from`/`zip_to`/`vat_required`
drive automatic detection on the partner; `account_ids`
(`account.fiscal.position.account`) and `tax_ids`
(`account.fiscal.position.tax`) are the actual account/tax substitution maps
applied when computing invoice lines. `foreign_vat` + company's own VAT-per-
country registration is the AR/EU "sell abroad without a subsidiary" case —
out of scope for a normal single-country implementation.

## `account.report` / `account.report.line` / `account.report.expression`

All three are defined in core `addons/account/models/account_report.py` — the
Enterprise `account_reports` module inherits and extends them, it does not
introduce the base structure.

```
account.report
  └─ line_ids: account.report.line          (rows, hierarchical via parent_id/children_ids)
        └─ expression_ids: account.report.expression   (one per column, computes the cell value)
  └─ column_ids: account.report.column       (columns; each references an expression label)
```

`account.report.expression` fields (`account_report.py:537-575`):

```python
engine = fields.Selection([
    ('domain', "Odoo Domain"),
    ('tax_tags', "Tax Tags"),
    ('aggregation', "Aggregate Other Formulas"),
    ('account_codes', "Prefix of Account Codes"),
    ('external', "External Value"),
    ('custom', "Custom Python Function"),
], required=True)
formula = fields.Char(required=True)
subformula = fields.Char()
date_scope = fields.Selection([...], default='strict_range')
label = fields.Char(required=True)   # e.g. 'balance' — how other expressions/columns reference this one
```

| Engine | `formula` holds | Notes |
|---|---|---|
| `domain` | an `ast.literal_eval`-able Odoo domain on `account.move.line`, validated at save (`_check_domain_formula`, `account_report.py:605-613`) | requires a `subformula` (SQL constraint `domain_engine_subformula_required`, `:586-588`) — usually the sign/`balance` accessor |
| `account_codes` | account code prefixes, e.g. `"6 + 7"` | sums balances of accounts whose code starts with any listed prefix |
| `tax_tags` | a tag name (without the leading `+`/`-` sign) | pulls posted `account.move.line.tax_tag_ids` matching that tag for the report's country — this is the VAT-book/tax-report mechanism |
| `aggregation` | a formula referencing other lines' expressions by code, e.g. `"line_1.balance + line_2.balance"` | can't be combined with `groupby`/`user_groupby` on the line (`_validate_engine`, `:621-630`) |
| `external` | `most_recent` / `sum` / a manual-entry marker | value comes from `account.report.external.value` records, not computed from moves — used for lines a human fills in |
| `custom` | dotted path to a Python method on an `account.report.custom.handler` | escape hatch for logic no other engine can express |

Each `account.report.line` also exposes shortcut fields —
`domain_formula`, `account_codes_formula`, `aggregation_formula`,
`external_formula`, `tax_tags_formula` (`account_report.py:350-355`) — that
exist purely to shorten XML: setting one calls `_create_report_expression`
(`:466-497`) which builds the matching `account.report.expression` record for
you, still on the same six engines above. Use the shortcut in new report XML;
both forms produce identical `account.report.expression` rows.

### Customizing a report — inherit lines/columns via XML, don't fork the report

```xml
<record id="account.generic_tax_report" model="account.report">
    <field name="line_ids" eval="[Command.create({...})]"/> <!-- or -->
</record>

<!-- more commonly: add a line as its own record, parented into the existing report -->
<record id="my_module.tax_report_extra_line" model="account.report.line">
    <field name="report_id" ref="account.generic_tax_report"/>
    <field name="parent_id" ref="account.generic_tax_report_line_xxx"/>
    <field name="sequence">50</field>
    <field name="code">MY_EXTRA_LINE</field>
    <field name="tax_tags_formula">MyTag</field>
</record>
```

Add rows by creating new `account.report.line`/`account.report.expression`
records that reference the existing `report_id`/`parent_id` (or by editing the
`*_formula` shortcut on a line you `_inherit`-loaded via `ref`), rather than
writing a whole new `account.report`. A country-specific variant of a base
report (e.g. a VAT report per AFIP responsibility type) uses
`root_report_id` to stay linked to the generic one for menu/comparison
purposes while carrying its own `country_id` and `availability_condition`
(`country`/`coa`/`always`).

## `accountant` dependency (workspace rule)

Any module that creates, posts, pays, or **displays** an invoice/bill must
depend on the Enterprise **`accountant`** module in its manifest, not bare
`account`. `account` installs the data model; `accountant` (parent of
`account_accountant`) is what puts the Accounting menu itself in the UI. A
module depending only on `account` can create an `account.move` that is
perfectly valid in the database and invisible to the user — "it didn't create
the invoice" and "I can't see the invoice" look identical from the UI and are
not the same bug. Before testing any invoicing flow in any base (local
included), install `accountant` first — see root `CLAUDE.md` § *Invoicing means
`accountant`* and § *Before touching a database*.

## Gotchas vs assumptions

| Gotcha | Detail |
|---|---|
| `is_invoice()` includes credit notes | `out_refund`/`in_refund` pass `is_invoice(False)` — use `move_type == 'out_invoice'` for "sale invoice, not a credit note" (`account_move.py:5850-5868`) |
| `price_include` is computed, not settable | 18.0 moved the boolean to `_compute_price_include` off `price_include_override`; writing `price_include` directly on a new tax does nothing useful (`account_tax.py:127-131`, `261-269`) |
| Reload vs fresh install of a chart template | `template_code == company.chart_template` flips `_load` into `_pre_reload_data` (update) instead of create; template data added by a later-installed module needs an explicit reload with `force_create=True` to reach already-onboarded companies (`chart_template.py:203-231`) |
| `account.report.expression` is core, not Enterprise | `account_reports` (Enterprise) only `_inherit`s it for the engine/UI — the model, the six engines, and the formula shortcuts all live in `addons/account/models/account_report.py` |
| `_post()` vs `action_post()` | `action_post` adds the abnormal-amount/date wizard gate and calls `_post(soft=False)`; calling `_post` directly from code skips that wizard but still enforces `account.group_account_invoice` and the invoice-completeness checks (`account_move.py:5084-5122`, `5541-5562`) |
| `account.group` code ranges are computed, not authored | `code_prefix_start`/`code_prefix_end` are `compute=..., store=True, readonly=False, precompute=True` — they auto-derive from account codes; manually setting them out of sync with actual accounts just gets recomputed away (`account_account.py:1453-1454`) |
