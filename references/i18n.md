# i18n — Odoo 18 translations

This module's rules on top of Odoo's: every user-facing string is English in
code and views; Spanish lives only in `i18n/es_AR.po`, without accents. See
root `CLAUDE.md` "Manifest conventions" and `odoo-slop-audit` C1/C2 for the
workspace-level version of this rule; this file is the mechanics.

## `_()` — the translation call

Two equivalent entry points exist in 18, verified in
`odoo/tools/translate.py` and `odoo/api.py`:

```python
from odoo.tools.translate import _
...
raise UserError(_("Invalid quantity for %s", product.display_name))
```

```python
# newer form, resolves the module from the environment automatically
self.env._("Invalid quantity for %s", product.display_name)
```

`env._` is defined at `odoo/api.py:788-810` (`Environment._`); `_ =
get_text_alias` is defined at `odoo/tools/translate.py:734`. Both are the
module-level `_` you `import`, or `self.env._`, are interchangeable for
plain (non-lazy) code — pick one per file and stay consistent.

### Rules

- **Always wrap** any string a user reads: `UserError`, `ValidationError`,
  `Warning`, notifications, `_description`/`string`/`help` values built
  dynamically. A bare `raise UserError("...")` is never translatable — this
  is `odoo-slop-audit` C2, treat it as a BLOCKER finding.
- **Pass arguments to `_()`, never pre-format the string:**

  ```python
  # correct — translators see one template with a placeholder
  _("Scheduled meeting with %s", invitee.name)

  # wrong — translators see a different literal string per invitee
  _("Scheduled meeting with %s" % invitee.name)
  _(f"Scheduled meeting with {invitee.name}")
  ```

  `get_text_alias`/`env._` accept **either** positional args **or** keyword
  args, never both (`odoo/api.py:805`, `assert not (args and kwargs)`):

  ```python
  _("Missing value for %(field)s on %(model)s", field=name, technical_name=model)  # kwargs
  _("Missing value for %s on %s", name, model)                                      # positional
  ```

- **Only literal strings are extracted.** `_()` around a variable or an
  f-string is invisible to the `.pot` extractor — the extractor greps for
  the literal template, it does not evaluate the code. This also means the
  string argument itself cannot be built with `+` or `%` before reaching
  `_()`.
- **Keep the whole sentence in one call.** Splitting a message across two
  `_()` calls concatenated with `+` loses word-order context for languages
  where the pieces don't reorder the same way, and breaks pluralization.
- **Never call `_()` inside a genexp/comprehension/lambda.** Verified
  workspace gotcha (see memory `odoo-underscore-traduccion-frame-llamador`):
  the classic `_` implementation walks the call stack (`_get_lang`,
  `translate.py:600-615`) to find the caller's `self`/environment; inside a
  generator expression or lambda the frame it lands on is the generator
  machinery, not your method, so the language lookup silently fails and the
  string is returned untranslated instead of raising. Use an explicit
  `for` loop when the body calls `_()`.

## `_lt` — module-level lazy translation

A translation needed at **import time** (a module-level constant, a
`Selection` list built outside a method) cannot resolve a language yet — no
request/environment exists. Use lazy translation instead, which defers the
actual lookup to `__str__` / display time:

```python
from odoo.tools.translate import LazyTranslate
_lt = LazyTranslate(__name__)

STATE_LABELS = _lt("Draft")   # not resolved yet — just holds the template
```

`_lt = LazyGettext` (`odoo/tools/translate.py:735`) is the bare callable form;
`LazyTranslate(__name__)` (`translate.py:711-731`) is the module-scoped
factory that also pins the correct module name for term lookup, which
matters because `_lt` at class-body scope runs during import, when stack
introspection may not find the right addon. Prefer
`_lt = LazyTranslate(__name__)` at the top of the file over the bare
`from odoo.tools.translate import _lt` for anything beyond a one-off.

Resolve a lazy value explicitly when you need the string now:

```python
self.env._(LABEL)   # or: str(LABEL)
```

`LazyGettext.__eq__`/`__lt__` raise `NotImplementedError` on purpose
(`translate.py:684-696`) — comparing a lazy value directly (`if label ==
"Draft":`) is a bug by design; compare `str(label) == "Draft"`.

## Translatable fields

```python
name = fields.Char(translate=True)
description = fields.Html(translate=True, sanitize=False)
```

`translate=True` on `Char`/`Text`/`Html` (`odoo/fields.py:2086-2091`,
`:2126-2130`) stores one value per active language in `ir.translation`-backed
storage and serves the record's field in the current user's language
automatically — no `_()` needed for field *values*, only for code-authored
messages. `translate` may also be a callable for term-level (not whole-value)
translation; the plain `True` case is what covers nearly every field.

## XML views

View labels (`string=`, `help=`) are translated automatically by the
`.pot` exporter — no explicit marker needed in XML, unlike Python. This
workspace's rule stands regardless: the English string goes directly in the
view attribute, the Spanish translation goes only in `i18n/es_AR.po`, never
a hardcoded Spanish `string=`.

## `.pot`/`.po` files and export

```
<module>/i18n/
├── <module>.pot     template — regenerated, not hand-edited (this workspace has no .pot committed)
└── es_AR.po         the only translation file per this workspace's convention
```

CLI export/import (`odoo/tools/config.py:277-294`, verified):

| Flag | Effect |
|---|---|
| `--i18n-export=<file>` | export all extracted terms to `.csv`, `.po`, or `.tgz`; requires `-d` |
| `--i18n-import=<file>` | import a `.csv` or `.po`; requires `-l <lang>` |
| `-l`, `--language=<code>` | language code for export/import, e.g. `es_AR` |
| `--i18n-overwrite` | overwrite existing translation terms on module update or import (default: keep existing) |
| `--modules=<mod1,mod2>` | restrict export to specific modules, used with `--i18n-export` |
| `--load-language=<codes>` | languages to activate/load on server start |

Typical export for this workspace, against the Docker lab:

```
odoo-bin -c /etc/odoo/odoo.conf -d <db> --i18n-export=i18n/es_AR.po \
  --modules=<module> -l es_AR --stop-after-init
```

## `es_AR` gotcha — workspace-specific

Odoo does **not** ship an `es_AR.po` base translation; `es_AR` falls back to
the generic `es_419` (Latin American Spanish), and standalone `es` (Spain)
terminology differs from Argentine usage for accounting/commercial terms.
Never invent or assume the Argentine term when writing `es_AR.po` entries —
check the running database's actual loaded terms for that key first (see
memory `odoo-es-ar-cae-en-es419-no-es`).

## Workspace-specific string rules

Per root `CLAUDE.md`:

| What | Rule |
|---|---|
| `string=`, `help=`, view labels | English, always |
| `UserError`/`ValidationError`/notifications | English, wrapped in `_()` |
| Spanish text | `i18n/es_AR.po` only, **no accents** (ASCII) — never in the manifest, never hardcoded in Python/XML |
| Code comments | follow the module's existing language (not forced to English) |

Converting a module's legacy Spanish-hardcoded labels to English is a
separate, deliberate pass — safe at any time since a label is display-only
and needs no data migration, but never bundled silently into an unrelated
change (it inflates the diff and triggers the same odoo.sh `-u` cost as any
other file touch — see `migrations-upgrades.md`).
